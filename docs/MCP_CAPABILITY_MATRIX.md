# Draw MCP capability matrix

## V2 issue #33 delivery status

The #33 implementation branch adds native scene editing, selection/group/arrange/delete/duplicate, guarded undo/redo, title/background and viewport controls, paginated revision-aware reads, plus MCP open/save/export tools. Dirty `open_document` uses an expiring, one-use token: Draw displays the request, the human approves or denies it in the editor, and the MCP caller must retry with the token. The bridge binds approval to the active document/revision, filename, and SHA-256 of the source file; stale or expired requests do not open anything. File access is restricted to basename paths in `DRAW_MCP_DOCUMENT_DIR`.

**Current security boundary:** editor-tab sessions and MCP host identities are separate. The active editor tab must authenticate before document sync, command/flush acknowledgements, human approvals, or client revocation. MCP host calls must present the capability received through the human-approved `pair_mcp_client` flow; the bearer is stored by the host in a permission-restricted local file and Draw persists only its hash. The one-time pairing secret is displayed in Draw and copied by the human into protected MCP host configuration; it is never a tool argument/result, URL, or log. Secret issuance is throttled to one request every five seconds. The Vite development bridge sends MCP calls over loopback HTTP. A local loopback process can submit wrong pairing secrets and cause a pending secret to be invalidated or its attempt budget locked; it can deny pairing but cannot gain access, pair a client, or revoke the editor lease. The installed runtime routes MCP calls through a private per-user Unix socket (directory mode `0700`, socket mode `0600`); production loopback HTTP rejects MCP-only routes before authentication/lockout state is accessed. The development bridge is not a sandbox against a fully compromised process running as the same OS user, which may inspect that user's memory or credential files; the same-OS-user trust boundary also applies to the installed runtime. See [#28](https://github.com/ashbhati/draw/issues/28) for supported platform scope and release status.

MCP saves create new files atomically and fail with `PATH_EXISTS` when a target already exists. Overwrite is intentionally unavailable: the macOS and Linux native rename flags reviewed for this feature provide either no-replace or unconditional swap/exchange, not compare-and-swap against the file identity approved by a human. Rechecking a hash and then renaming would retain a race with another local process. See [the #39 feasibility record](ISSUE_39_SAFE_REPLACEMENT.md) and [issue #39](https://github.com/ashbhati/draw/issues/39); current safe behavior is to save under a new filename. Durable MCP actor identity and undo eligibility across reloads/restarts are tracked separately in [#38](https://github.com/ashbhati/draw/issues/38); this branch fails closed when it cannot prove an operation remains eligible.

This document translates the V2 goal—agents should be able to do the meaningful work available to a person in Draw—into a reviewable capability and safety contract. The target is **semantic capability parity**, not a remote imitation of every mouse gesture: an agent requests an operation such as “create a labeled box”, while the editor remains responsible for rendering, hit testing, and canvas interaction.

## V2 issue #38 delivery status

The local editor now stores MCP operation results and the current document in one IndexedDB transaction. Scene and viewport mutations require a caller-provided `idempotencyKey`; retries with the same authenticated client identity, key, and canonical payload return the original operation result, while a changed payload conflicts. Both document and view revisions are checked atomically; viewport operations are idempotent and do not enter scene undo history. Full results are retained for seven days; compact payload-hash tombstones are retained for up to 30 days and 10,000 entries per document/client pair. The transaction checks the stored base revision, duplicate key, and undo/redo target before writing. Actor-bound undo/redo snapshots expire after seven days and are pruned to at most 100 document snapshots during periodic maintenance (every 32 successful MCP commits). Malformed optional history does not prevent loading the validated drawing; that specific undo/replay fails closed, and maintenance skips and removes unreadable ledger rows. These records are app-local IndexedDB data and are not embedded in portable `.draw` files; `.draw` scene content and revision migrations remain readable independently.

## V2 issue #52 delivery status

Workspace lifecycle is exposed to paired MCP clients through `list_workspaces`, `list_canvases`, `create_workspace`, `rename_workspace`, and `select_workspace`. Draw now presents one board per workspace. The legacy canvas-named tools remain compatible: `create_canvas` creates a new workspace and board using the requested name; `duplicate_canvas` creates a new workspace named from the requested name or `<source board> copy`; `import_draw_file_as_canvas` creates a new workspace named from the requested name or imported document title. Each operation returns the actual workspace and canvas IDs. `rename_canvas` renames that workspace's sole board/document title; `select_canvas` selects the board's owning workspace and validates the supplied workspace ID. `list_canvases` returns the one board belonging to the requested workspace. Catalog reads return stable IDs, active IDs, `catalogRevision`, and the active editable document with its document/view revisions. Mutations require the current `expectedCatalogRevision` and an `idempotencyKey`; compact result identifiers and the workspace/document mutation are committed in one IndexedDB transaction. Exact retries rebuild the response from current storage before checking the advanced catalog revision; they never restore an old active-document snapshot. Reusing a key with a different caller or payload conflicts. Receipts expire after 30 days and are capped at 1,000 entries; deletion atomically removes receipts that refer to deleted workspaces.

Import accepts only a plain `.draw` filename inside `DRAW_MCP_DOCUMENT_DIR`, validates it, and creates a new workspace containing one board with a new document ID while preserving the scene and assets. It does not call `open_document` or replace the existing workspace. `delete_canvas` is rejected with guidance to use `delete_workspace`, because a board is the entire contents of a workspace. Deleting a workspace requires one-use human approval in the active Draw tab, bound to the target, catalog revision, active document/revision, and idempotency key; approval covers the board, workspace library, and local history. The editor derives the displayed workspace name from its local catalog; request-supplied display strings are ignored. Denied, stale, or expired approvals do not delete data. MCP receipts remain local IndexedDB state and are not embedded in `.draw` files.

## V2 issue #11 reusable library delivery status

Reusable items and their embedded assets are workspace-scoped in IndexedDB and are not embedded in `.draw` files. The library record carries a monotonic `libraryRevision` and bounded receipts for authenticated `(workspaceId, clientIdentity, idempotencyKey)` mutations. Add, rename, and delete validate `expectedLibraryRevision` and canonical payload hash atomically; exact retries return the original result, while a changed payload or stale revision conflicts. Approved delete retries may reuse the exact same caller-bound confirmation fingerprint only to reach that durable receipt; a different operation still requires fresh human approval. Library snapshots from Excalidraw's callback are ignored in read-only tabs, skipped when semantically unchanged, and compare-and-swap saved against their loaded library revision. UI and MCP add/rename/delete use item-level mutations against the latest stored record.

Status labels below distinguish implemented behavior from proposed capability. The #31/#33 rows remain a historical map of the initial phase; see the delivery sections above for the later #11 and #52 implementations.

## V2 phases

These phases are a proposed order, not a release commitment. They keep file safety and protocol decisions ahead of broad tool implementation.

1. **Phase 0 — Contract and threat boundaries (#31):** approve the matrix, schemas, revision/idempotency ownership, undo policy, local-file permissions, and open/switch/overwrite confirmations.
2. **Phase 1 — Native authoring (#32):** create core Draw elements and relationships through MCP; verify an agent-created file opens and a human can edit it.
3. **Phase 2 — Scene editing and document lifecycle (#33):** edit/arrange/history, background/viewport, read/save/open/export; preserve editable `.draw` state and protect concurrent human edits.
4. **Phase 3 — Workspaces (#34):** migrate the existing single local document into project organization without data loss.
5. **Phase 4 — External image search (#35):** search, inspect rights metadata, then embed the chosen image and its attribution. Reusable local library additions remain tracked separately in #11.
6. **Cross-cutting packaging (#28):** production MCP runtime and end-user install path are prerequisites for a distributable release, rather than a prerequisite for local development work.

## Identifier, revision, and pagination proposal

- `documentId` is the stable identity of one Draw document. The current V1 summary returns it under the field name `id`; V2 should expose `documentId` and may keep `id` as a deprecated alias for compatibility. It is distinct from workspace/canvas display names.
- Every scene object has a Draw-generated stable `elementId`. Caller-supplied node keys are request-local aliases only; responses map them to persistent Draw IDs. IDs are scoped to one document.
- V2 responses include two monotonically increasing revisions owned by the Draw application/document store, not by the stdio MCP process or Vite bridge: `documentRevision` for scene/content/layout, and `viewRevision` for viewport. Both are persisted in local autosave and `.draw` metadata. V1 documents migrate to initial revisions (for example 0/0); document identity changes start a new revision namespace.
- Element creation/update/delete/arrangement, text, assets, title, and background increment `documentRevision`. A human pan/zoom or MCP viewport/fit operation increments `viewRevision` only, so ordinary navigation does not invalidate an agent's scene edit. Transient selection/focus increments neither. Scene undo/redo increments `documentRevision`; viewport-only history, if provided, increments `viewRevision` only. Revisions never move backward.
- Human viewport gestures are coalesced: pan/zoom events update transient view state, then increment and persist `viewRevision` once when the gesture settles (proposed 250 ms debounce after the final input). Explicit MCP viewport/fit operations commit once when complete. A page hide/reload flushes the final settled view where possible; intermediate pointer/wheel events do not each create a revision.
- Every mutation input includes `documentId`; scene mutations include `expectedDocumentRevision`, and viewport mutations include `expectedViewRevision`. The named document must be authorized for the caller and active/writable for the current tool operation; a mismatch returns a conflict without changing another document.
- One active writer owns a document. Preserve V1's writer lock/read-only tab behavior until V2 has a tested conflict-resolution model. Tab `clientId` is an ephemeral routing identity and may change on reload; it is not the durable identity used for idempotency. On reload Draw restores the persisted `documentRevision` and `viewRevision`; stale in-flight acknowledgements from the prior tab client are rejected.
- `get_current_canvas` returns `documentId`, both revisions, and a cursor pinned to `documentRevision` (not `viewRevision`). Viewport changes do not invalidate scene pages. If scene revision changed, return a conflict and require a fresh first-page read; do not silently shift offsets. Cursor data is derived from document ID/revision/offset or backed by an equivalent immutable snapshot, so it remains valid across reload when the same scene revision is still available.
- Each MCP installation is paired through the human-approved bootstrap in the Local bridge threat model and receives a stable random `clientIdentity`, persisted by Draw's MCP configuration/local settings and supplied by the MCP client on every call. This survives browser/tab reloads and MCP subprocess restarts; it is separate from the ephemeral tab `clientId` used to route to the active editor.
- Every mutation input includes `documentId`, `clientIdentity`, `idempotencyKey`, and the relevant expected revision. Draw computes a canonical hash of the fully validated operation payload, including `documentId`. The ledger key is `(documentId, clientIdentity, idempotencyKey)`. Retain full completed operation records for **7 days** from completion in Draw's durable local application store. Keep compact key/hash tombstones for at most **30 days** and **10,000 entries per document/client identity**, evicting oldest first. A replay during the 7-day window with the same key and hash returns the original `operationId`/result; reuse with a different payload returns `IDEMPOTENCY_KEY_REUSE` and never applies the new payload. Authenticate the caller before returning a replay, then check a valid caller's idempotency record before its current revision.
- Atomically commit each document revision and its operation result. A restart then has a deterministic outcome while a record/tombstone is retained: a durable operation record replays its result; an expired-result tombstone returns `OUTCOME_UNKNOWN` with `reason: idempotency_expired`. If neither exists, use the original `expectedDocumentRevision` as the safety guard. Apply only if it still matches; because revisions are monotonic, an earlier successful mutation with that expected revision would have advanced the document beyond it. If the revision is stale, return `CONFLICT` and require a fresh read/reconciliation and a new key. After tombstone eviction the historical outcome may no longer be known, but a stale revision still prevents reapplication. A stdio server may cache results but is not authoritative.
- The Vite bridge's generated command IDs remain transient routing IDs; durable operation identity is the authenticated `(documentId, clientIdentity, idempotencyKey)` record in IndexedDB. The 20-second bridge command timeout and 60-second late-ack retention are transport behavior only; MCP's HTTP wrapper times out at 25 seconds. On timeout, retry the same operation with the same key and payload to replay a retained result, or read the canvas and reconcile. A tombstone returns `OUTCOME_UNKNOWN`; do not blindly retry with a new key.

## Mutation and undo/redo semantics proposal

- Validate the full batch before applying. Prefer atomic all-or-nothing behavior; if any operation supports partial results, return explicit per-element statuses and the resulting revision.
- A successful logical MCP scene mutation is one history transaction. Record its `operationId` and actor (the authenticated stable MCP `clientIdentity`) in the same IndexedDB transaction as the new document revision and result. Viewport-only changes are not scene history transactions. Mutation responses include `persisted` and any bridge-sync warning. If the atomic local commit fails, do not apply the scene change or claim success. The Vite bridge's command IDs remain transient routing IDs and are not operation identity.
- `undo_operation(operationId)` and `redo_operation(operationId)` only reverse/reapply that MCP actor's latest still-eligible scene operation, using durable before/after snapshots instead of Excalidraw's volatile keyboard history. The transaction rechecks actor, operation ID, document revision, and semantic scene snapshot before applying. If any human/other-client scene change followed it, return `CONFLICT` without changing the canvas. A later viewport-only `viewRevision` change does not block scene undo/redo.
- A human keyboard Undo may undo the latest scene operation from any actor, including an MCP mutation. Every successful scene undo/redo is itself a new persisted state and increments `documentRevision`; it never decrements or reuses a prior revision. If an app later adds undoable viewport history, that action increments `viewRevision` only.
- Redo is bound to the operation just undone and its resulting `documentRevision`. A newer scene edit clears or conflicts the redo target; a pan/zoom does not. Never replay stale state over new work.
- Timed-out mutations are resolved by retrying with the same authenticated identity, idempotency key, and canonical payload or re-reading the canvas. A retained completed record returns the original result without reapplying; a tombstone returns `OUTCOME_UNKNOWN`, requiring reconciliation and a new key. When no record remains, the atomic document/view base-revision check prevents stale scene or viewport writes. Never blindly retry an expired create. A timeout does not imply the scene change failed.

## File and local-data safety proposal

The installed MCP runtime remains local-first and loopback-bound, per #28. An MCP stdio subprocess does not, by itself, grant permission to access arbitrary filesystem paths.

- Default tools operate on the document named by `documentId`. `open_document` may read a relative path only inside the canonical, user-configured Draw directory, or accept a client-provided artifact/resource reference. It cannot read an arbitrary absolute path; the MCP client cannot grant itself a new root.
- A user may explicitly configure one local Draw directory for MCP file operations. Canonicalize the configured root and candidate parent, resolve symlinks, and reject path traversal or any target that resolves outside the root. Do not follow target symlinks or allow symlinked path components.
- Inputs validate actual file content, not trust the filename or MIME claim. `.draw` bytes must parse as a supported Draw format and match the `.draw` extension when a path is used. The maximum `.draw` size is 100 MiB of **decoded raw file bytes**. Do not send large document bytes through model context: use an MCP artifact/resource or approved local path by default. Proposed inline arguments cap at 1 MiB decoded raw content; ordered transfer chunks cap at 1 MiB decoded raw bytes each. Separately cap each encoded JSON/MCP chunk envelope at 2 MiB and each complete JSON command envelope at 4 MiB, including metadata/base64 expansion. If image support is later specified, cap each decoded raw image at 20 MiB and enforce decoded pixel dimensions; #32 does not accept images. Verify decoded byte counts and SHA-256 before parsing/commit.
- Output extensions are restricted to `.draw`, `.png`, `.jpg`, or `.jpeg` and must case-insensitively match the requested output type. Normalize names to Unicode NFC. Draw serializes its own writes under a per-canonical-directory lock and checks case-folded names before commit. This reduces collisions among Draw operations; on a case-sensitive filesystem, the case-fold scan is best-effort against non-Draw writers and cannot guarantee uniqueness if another process races in a differently cased name. For exact target collisions, write and flush a temporary file in the same approved directory, then commit a new file with an OS-supported atomic no-replace primitive. If the exact target appears or a detected case-folded collision exists, return `PATH_EXISTS` with no partial final file; fail closed if atomic no-replace is unavailable.
- Save to a new, non-existing path is allowed inside the configured root via the no-replace atomic write above. Save to an existing path returns `PATH_EXISTS`; overwrite is deferred to [#39](https://github.com/ashbhati/draw/issues/39). Open of dirty content returns a one-use token with a two-minute expiry. In the current development bridge this is only a UX confirmation: caller-supplied `clientId` is not an authenticated identity, and local callers may spoof approval. Authenticated sessions are tracked in [#41](https://github.com/ashbhati/draw/issues/41).
- Confirmation tokens are one-use, bound to the active document/revision, requested filename, and source file hash; stale or expired tokens do not open anything. The current bridge binds approval to caller-supplied `clientId`, which does not authenticate local callers; see [#41](https://github.com/ashbhati/draw/issues/41).
- Opening a document that would discard unsaved active state similarly requires the UI confirmation above. A normal project/canvas switch preserves both documents and does not need destructive replacement. No MCP flag or model-provided string bypasses confirmation.
- For an approved overwrite, hold the per-directory serialization lock and a per-path lock, recheck the target identity/hash, then use an atomic conditional replacement. If the OS/filesystem cannot guarantee the target is still the confirmed file at replacement time, stop with `stale` and require the human to complete the overwrite through Draw's native save dialog; never fall back to blind replacement.
- Define and test limits for path length, body size, asset byte count, decompressed image dimensions, and allowed media formats. Do not render remote URLs on reopen. Sanitize SVG or reject it; embedded raster assets are the safe initial image format.
- MCP must never expose browser storage, credentials, local unrelated files, or arbitrary network fetch as part of canvas text interpretation.

### Local bridge threat model

- **Current V1 boundary:** the dev bridge binds to loopback, validates an allowlisted loopback Host/port, rejects a mismatched Origin when an Origin header is present, and checks JSON on mutations. The stdio client's local `fetch` omits Origin, so absence is currently accepted. These checks reduce remote-browser/DNS-rebinding exposure; they are not authentication.
- **Threat:** any other local process that can connect to loopback can omit Origin and spoof Host/Origin headers. Editor-side registration, document sync, command acknowledgement, flush acknowledgement, and confirmation response additionally require a per-tab credential; MCP reads, confirmation requests, and commands require the paired host capability. A caller-supplied `clientId` alone grants no editor authority. In the development bridge, an unpaired local process can send wrong pairing secrets and cause denial of service by invalidating the one-time secret or exhausting the pairing lockout; it cannot gain MCP access or revoke the active editor.
- **Editor-tab bootstrap (#41, implemented for the Vite development bridge):** Draw generates a random one-use launch code from a CSPRNG with **48 bits of entropy**, never derived from time, tab ID, or client ID. The human must start Vite from a trusted terminal they control, never from an agent/automation PTY, keep it open, and manually enter the code in the intended Draw tab's Connect MCP dialog. `stdout.isTTY` only confirms that output is attached to a terminal; it does not prove a human is present or that another same-user process cannot read that terminal. This is not a security boundary between processes running as the same OS user. No credential is placed in the URL, query, fragment, HTTP response to an unpaired caller, process arguments, server logger, or ordinary MCP tool result. The code expires after 60 seconds and is consumed once. An expired or superseded code does not consume a failed-attempt allowance. Connect MCP can ask the trusted terminal to reprint the still-valid code, or print a new code after expiry, without receiving it over HTTP; requests are throttled to one every five seconds. Five wrong codes invalidate future bootstrap attempts and persist a 15-minute lockout across runtime restarts, without revoking an already authenticated editor lease. Failures use generic responses. Successful exchange issues a 256-bit per-tab secret held only in browser memory and bound to the active editor lease. A new authenticated tab replaces the prior lease and invalidates pending editor acknowledgements/confirmations. With no interactive TTY, bootstrap and code reissue fail closed. This secret is distinct from a future paired MCP `clientIdentity`.
- **MCP pairing (#44, implemented for the Vite development bridge):** MCP pairing can start only after the human connects the editor tab, opens Draw's MCP clients dialog, and copies the displayed 256-bit single-use pairing secret into the trusted host's protected environment configuration. The stdio server reads `DRAW_MCP_PAIRING_SECRET` from that configuration, never from a tool argument or argv, then submits it over the loopback HTTP bridge. The code expires after five minutes. Draw presents the requesting client name and fingerprint in the authenticated editor, and issues a stable identity plus a 256-bit capability only after visible human approval. Re-pairing the same fingerprint revokes the previous client and warns the human before approval. Draw stores only the capability hash in a restrictive config file; the MCP process stores the capability in a mode-0600 credential file by default. `DRAW_MCP_CLIENT_CREDENTIAL_PATH` must be absolute; on POSIX, the credential file and its parent directory must belong to the current user, the file must be mode 0600, and the directory must not be group/world writable. Five invalid attempts trigger a persisted 15-minute lockout; attempts during lockout do not extend it, and the counter resets on expiry. Wrong loopback requests can consume that budget in development, as described above. Denial or expiry cannot revoke the existing editor lease. Commands, flushes, and confirmation tokens retain their authenticated MCP actor identity. Revocation cancels in-flight commands, reads, and confirmations belonging to that identity, rejects late acknowledgements with an explicit canceled response, and leaves other paired clients and the human editor connected. A command still awaiting acknowledgement is rolled back in place only if its current semantic document state (elements, assets, title, background, app state) remains equal to the baseline or command result, and the live viewport and selection still match those states. Editor-generated element version/index metadata and revision counters are ignored for this comparison; later human edits, selection changes, pans, or reopened documents are preserved. The editor is not remounted, preserving its history and selection; the canceled MCP operation may leave a no-op Undo entry before earlier history is reachable. A command already fully acknowledged before revocation is not rolled back. Production packaging must use authenticated IPC (for example, a Unix domain socket/named pipe with OS ACLs/peer credentials) so unpaired loopback callers cannot submit pairing attempts or consume the attempt budget; this is part of [#28](https://github.com/ashbhati/draw/issues/28), not claimed by #44.
- **V2 installed runtime:** require the paired capability on MCP bridge routes and the per-tab secret on editor-side registration/sync/ack routes. Issue the tab secret only after valid human entry of the one-use launch code and bind it to that launched editor session and active editor lease; never expose it to arbitrary loopback callers. Do not authorize using `clientId` alone. Only the active editor lease may sync the document or receive/ack commands. A new tab takeover atomically revokes the old tab secret/lease and invalidates pending command/flush acknowledgements. Require one-time command/flush nonces bound to the active lease, document ID, and revision; reject stale or replayed acknowledgements. Revoking a paired MCP identity blocks that MCP client's tool access and its pending commands, but does not revoke the human's editor-tab lease. Editor-tab revocation/takeover is a separate control.
- **Revocation and replay:** MCP identity revocation immediately blocks new reads/mutations and mutation replays for that identity and cancels its pending commands; it does not affect the human editor lease. A command already fully acknowledged remains in the document. If revocation races an unacknowledged command, Draw returns an explicit canceled acknowledgement and rolls the command back only while semantic canvas state and live viewport/selection still match; any subsequent human edit is preserved. The seven-day operation result remains available only to the human in Draw for diagnosis; a revoked client cannot query or replay it. Re-pairing creates a new identity and does not inherit old idempotency keys. Editor-tab lease revocation separately rejects that tab's syncs and late acknowledgements.
- **Limit:** this is local-app protection against unpaired local clients and remote web origins, not a sandbox against a fully compromised operating-system user or process that can read Draw's local credential store/config. State that boundary in the security documentation.
- **Tests:** verify correct/incorrect/missing tokens, revoked identity, loopback/non-loopback, allowed/forged Host, same/mismatched/missing Origin, mutation content type, and body-size limits. Editor-tab tests prove the tab secret is never placed in URLs, process arguments, server logs, or ordinary MCP results; verify the 48-bit one-use code, expiry, five attempts, code invalidation, generic errors, and persistent lockout. MCP pairing tests verify secret input is read from protected host configuration rather than tool arguments, approval shows the client name/fingerprint, the MCP result does not reveal the capability, host credential permissions, expiry/single use, five-attempt lockout, revocation, and editor-lease separation. Development tests must also show wrong pairing requests cannot gain access and clearly preserve the documented local loopback denial-of-service boundary. Production #28 tests must prove unpaired loopback calls cannot consume attempts through the authenticated IPC route. Prove reload/new sessions/restart cannot reset lockout. Prove unpaired processes cannot register/take over an editor, sync, or acknowledge commands; takeover invalidates only the old editor lease; MCP identity revocation blocks agent access but leaves the human tab lease valid. Persistence tests verify atomic commit recovery, same-process journal recovery before restart, absent record with matching revision permits exact-key retry, revision mismatch conflicts, retained tombstones return `OUTCOME_UNKNOWN` with `reason: idempotency_expired`, and tombstone eviction remains safe through expected-revision conflicts. Preserve no-Origin stdio only with a valid paired token.

Canvas text and labels are **untrusted data**, whether authored by the human or supplied by an agent. Return them as data fields, never as executable markup or instructions. Do not evaluate HTML/SVG/URLs or follow instructions found inside a label; when an agent consumes text from the canvas, it should treat that text as user content rather than as a system/developer instruction.

## `.draw` compatibility proposal

V1 uses a versioned JSON `.draw` format (`format: "draw"`, `formatVersion: 1`) containing document identity/title, infinite canvas background and viewport, native editor elements, app state, and assets. V2 MCP operates on this same document model and persists both `documentRevision` and `viewRevision`. MCP idempotency/undo ledgers live in local IndexedDB and are not serialized into `.draw`; portability of an exported `.draw` file does not imply that its MCP retry history transfers to another browser profile.

- MCP-authored documents validate as normal Draw documents and reopen in Draw.
- Preserve native element fields, text/container and arrow bindings, asset bytes/references and attribution, app state, background, viewport, and stable IDs.
- Never save only a raster image or simplified diagram representation in `.draw`. PNG/JPEG remain separate flattened exports.
- Keep V1 files readable. If revision or workspace metadata requires a new format version, provide a tested migration; preserve compatible unknown element metadata and never silently drop unsupported content.

## Product and implementation decisions (all proposals pending review)

- **Coverage meaning:** expose semantic document and scene capabilities, not every cosmetic preference or low-level pointer gesture.
- **Active context:** scene tools act on the active board. Workspace operations require an explicit workspace/canvas ID and catalog revision; they may intentionally switch to that workspace's sole board. `open_document` replacement of dirty content returns `NEEDS_CONFIRMATION`; creating/switching workspaces preserves the prior board.
- **Undo ownership:** the agent can undo only its own latest eligible operation; later human/other-client work blocks that undo. The human's ordinary Undo can reverse the latest transaction, including an agent's.
- **Filesystem:** MCP resource/artifact is default for `.draw` and image output; direct read/write is optional only under the explicitly configured Draw root. New files are permitted there; existing-file replacement always requires the app UI confirmation described above.
- **Payload limits:** `.draw` total cap is 100 MiB decoded raw bytes; inline arguments cap at 1 MiB decoded raw bytes; ordered chunks cap at 1 MiB decoded raw bytes each; encoded chunk envelope caps at 2 MiB and complete command envelope at 4 MiB. Use artifacts/resources for large files and keep them out of model context.
- **Assets:** #35 owns online Openverse search/insertion, review, validation, embedding, and attribution. Search and insertion use fixed provider endpoints and Openverse IDs; MCP must never fetch a caller-provided URL. Reject redirects; requests, metadata, and body reads time out. Accept PNG/JPEG only, reject SVG, cap each fetched asset at 2 MiB and 16 megapixels, verify MIME against file signatures, and retain creator/source/license metadata in the embedded asset and `.draw` element. File-supplied claims are normalized, HTTPS links only are rendered, and those claims are labeled unverified. Attribution metadata remains in the `.draw` file and MCP image results. The human Image credits report was removed in #63; there is no in-app credits report. Review provider terms and each item's license rather than treating an index result as a legal guarantee. Local file import and other providers remain separate follow-ups unless added to #35.
